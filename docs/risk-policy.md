# Прозрачные правила учебного кредитного конвейера

## Назначение и границы

`DEMO_RULES_V1` — небольшой набор детерминированных правил для синтетических сценариев хакатона. Он показывает объяснимые переходы заявки, проверку полноты данных и расчёт доступной суммы. Это не статистическая или обученная модель, не оценка реальной кредитоспособности и не вероятность дефолта. Ни один результат не создаёт договор, перевод денег или обращение в БКИ/ФНС.

Реализация использует только стандартную библиотеку Java и `BigDecimal`. В ней нет ML, AutoML, новостей, сетевых запросов, случайности или чтения системных часов. Конкретные значения ниже — настраиваемые допущения демонстратора из командной wiki и явно описанных решений реализации. Они не объявляются требованиями законодательства или подтверждённой политикой банка.

Исходные ориентиры: приложенные `research/wiki/Credit-Pipeline-and-Risk-Engine.md`, `research/IMPLEMENTATION_BRIEF.md` и реализационный prompt. Wiki snapshot: `43940dea4636beebb909a66c0e005c7f72b5e768`. Рабочий контракт исходного приложения имеет приоритет над противоречащими ему страницами wiki.

## Небольшой Java API

```java
RiskEngine engine = new RiskEngine(DemoRiskPolicy.defaults());
Assessment assessment = engine.assess(snapshotInputs, originalRequest);
TermsEvaluation checked = engine.evaluateTerms(snapshotInputs, originalRequest, proposedTerms);
```

`assess` возвращает рекомендацию, причины и вычисления. `evaluateTerms` повторно проверяет тот же неизменяемый snapshot перед одобрением сотрудником или формированием предложения. Сервис обязан дополнительно проверить роль, владельца, состояние заявки, ожидаемую версию и ключ повтора в своей транзакции. Калькулятор не выполняет переходы в БД.

`LoanRequest` содержит `amountRub` и `termMonths`. `LoanTerms` добавляет `annualRatePercent`. Сохраняется существующий контракт: **100 000–50 000 000 целых рублей, 1–60 месяцев**. Денежные признаки и платежи имеют точность до копейки. В минимальном сценарии сотрудник меняет только сумму предложения; срок и ставка остаются рассчитанными для исходного запроса. Изменение срока или ставки в `evaluateTerms` отклоняется.

`DemoRiskPolicy` — неизменяемая конфигурация с группами `Product`, `Stops`, `Freshness`, `Scoring`, `Affordability`. Все границы вынесены из расчётных ветвей в эти группы. Изменение настроек требует отдельного идентификатора версии и сохранения соответствующей версии при фиксации snapshot/результата. `withRates(newVersion, greenRate, manualRate)` предназначен для явных вариантов, включая тест нулевой ставки; менять ставку с прежним именем версии нельзя. Баллы четырёх факторов являются фиксированной частью алгоритма версии V1; их изменение также требует новой версии кода и правил.

## Неизменяемые входы и происхождение

`RiskInputs` — Java record с защитной копией списка. `null` в обязательном поле остаётся неизвестным значением и не превращается в ноль/`false`. Оценка всегда использует сохранённый `asOf`; часы внедряются в сервис создания snapshot или mock-провайдер, а не читаются во время оценки. Повторная обработка или перезапуск не меняет дату, окно данных и свежесть исходного расчёта.

| Поле | Формат / единицы | Значение |
|---|---|---|
| `asOf` | Дата `YYYY-MM-DD` | Фиксированная дата снимка и оценки |
| `registeredOn` | Дата | Государственная регистрация синтетического бизнеса; отдельна от возраста счёта |
| `accountOpenedOn` | Дата | Открытие счёта; возраст в полных месяцах для балльного фактора |
| `directorChangedOn`, `soleFounderChangedOn` | Дата или `null` | Последняя смена директора / единственного учредителя |
| `managementHistoryComplete` | `true` / `false` / `null` | Только `true` подтверждает полноту истории; тогда отсутствующая дата означает отсутствие события |
| `cashflows` | 12 объектов `MonthlyCashflow` | Уникальные последовательные закрытые месяцы, заканчивающиеся предыдущим календарным месяцем относительно `asOf` |
| `cashflows[].month` | Месяц `YYYY-MM` | Месяц операции |
| `cashflows[].netCreditTurnoverRub` | RUB, ≥ 0, до 2 десятичных знаков | Кредитовый оборот после исключения внутренних переводов mock-провайдером |
| `existingDebtPaymentRub` | RUB/месяц, ≥ 0, до 2 десятичных знаков | Совокупный внутренний и внешний платёж без двойного учёта; при неизвестной части весь итог неизвестен |
| `bureauScore` | Целое 0–1000 | Учебный балл синтетического отчёта |
| `maxOverdueDays24m` | Неотрицательное число дней | Максимальная просрочка в 24-месячном окне |
| `recentClosedOverdueDays12m` | Неотрицательное число дней | Максимальная закрытая просрочка в 12-месячном окне; не больше 24-месячного максимума |
| `taxBlocked`, `bankrupt`, `liquidating` | Nullable Boolean | Три независимых юридических признака синтетической справки |
| `internalSource`, `bureauSource`, `fnsSource` | `SourceEvidence` | Маркировка источника, версия набора и дата наблюдения |

Пример маркировки источника:

```json
{
  "source": "SYNTHETIC_BKI",
  "version": "DEMO_DATA_V1",
  "observedOn": "2026-10-23"
}
```

Допустимые значения `source` привязаны к полю: `SYNTHETIC_INTERNAL`, `SYNTHETIC_BKI`, `SYNTHETIC_FNS`. Это локальные mock-провайдеры, а не реальные интеграции. Источник без версии/даты или с неподходящей маркировкой считается неполным.

### Свежесть и качество

- БКИ и ФНС: возраст **не больше 30 дней включительно** относительно `asOf`.
- Внутренние данные: **не больше 45 дней включительно**, с обязательным полным месячным окном. Это явное допущение для месячной периодичности.
- Наблюдения, даты регистрации, открытия счёта или смены руководства в будущем недопустимы.
- Отрицательные/пропущенные денежные признаки, неполная история, повторные/незакрытые месяцы и противоречивые окна просрочек требуют `MANUAL_REVIEW`.
- Полный нулевой оборот не является «неизвестным» или «стабильным» доходом. Он даёт отдельную причину `ZERO_INCOME`: деление и предложение не выполняются.

Правила свежести применяются к времени snapshot. Они не утверждают, что такой же отчёт актуален на произвольную более позднюю дату. Обновление источников и повторный скоринг — отдельная будущая операция с новым snapshot; кнопка обновления экрана не переписывает сохранённые входы.

## Приоритет решений

1. **Известный жёсткий стоп из свежего соответствующего источника → `REJECTED`.** Он имеет приоритет над недостатком других данных. Все найденные жёсткие причины сохраняются.
2. **Неполные, устаревшие, противоречивые или непригодные обязательные входы → `MANUAL_REVIEW`.** Балл и лимит не выдумываются.
3. **Полный балл меньше 500 → `REJECTED`.** Мягкое предупреждение или доступная сумма не отменяет красную полосу.
4. **Балл 500–649 или мягкий стоп → `MANUAL_REVIEW`.** При полных входах рассчитанный лимит доступен сотруднику.
5. **Зелёный балл без мягких стопов → проверка доступности:** исходная сумма → `APPROVED`; доступная меньшая сумма от минимума продукта → `OFFER_PROPOSED`; отсутствие такого предложения → `REJECTED` / `NO_AFFORDABLE_OFFER`.

Положительный юридический признак из устаревшего отчёта не выдаётся за актуальный жёсткий факт: такая заявка попадает в ручное рассмотрение из-за устаревших данных. Результат содержит коды и человекочитаемые русские объяснения; цвета интерфейса должны дублироваться текстом.

### Жёсткие стопы

| Условие | Граница | Код |
|---|---|---|
| Налоговая блокировка | `taxBlocked == true` | `TAX_BLOCK` |
| Банкротство | `bankrupt == true` | `BANKRUPTCY` |
| Ликвидация | `liquidating == true` | `LIQUIDATION` |
| Просрочка в 24-месячном окне | **Более 90 дней**; 91 срабатывает, 90 не является жёстким стопом | `SEVERE_OVERDUE` |
| Возраст бизнеса | Раньше даты `registeredOn.plusMonths(6)`; ровно 6 календарных месяцев допустимы | `BUSINESS_TOO_YOUNG` |

### Мягкие стопы

| Условие | Граница | Код |
|---|---|---|
| Смена директора | Меньше 60 дней; 59 срабатывает, 60 нет | `RECENT_DIRECTOR_CHANGE` |
| Смена единственного учредителя | Меньше 60 дней | `RECENT_FOUNDER_CHANGE` |
| Падение оборота | Последний закрытый месяц **более чем на 35%** ниже среднего за 12 месяцев; ровно 35% допустимо | `TURNOVER_DROP` |
| Закрытая короткая просрочка | 1–30 дней в 12-месячном окне | `CLOSED_SHORT_OVERDUE` |
| Промежуточная просрочка | Максимум 31–90 дней в 24-месячном окне | `MODERATE_OVERDUE_HISTORY` |
| Доля платежей | **От 45% до 50% включительно** по запрошенной сумме | `BORDERLINE_DEBT_RATIO` |

Правило 31–90 дней закрывает явный пробел wiki; оно объявлено допущением демонстрации. Зелёный балл не отменяет мягкое предупреждение. При доле выше 50% зелёная заявка получает предложение/отказ по доступности; серая заявка остаётся в ручном рассмотрении с показанным лимитом.

## Балльная карта: максимум 850

| Фактор | Интервалы V1 | Баллы |
|---|---|---|
| Полные месяцы обслуживания | `>24`; `12–24`; `6–11`; `<6` | 200; 150; 80; 0 |
| Средний чистый оборот 6 месяцев | `>2 млн`; `[1 млн, 2 млн]`; `[500 тыс., 1 млн)`; `<500 тыс.` | 250; 190; 120; 50 |
| Синтетический балл БКИ | `700–1000`; `550–699`; `0–549` | 250; 150; 40 |
| Коэффициент вариации 6 месяцев | `<15%`; `[15%,30%]`; `>30%` | 150; 90; 30 |

Коэффициент вариации использует стандартное отклонение генеральной совокупности, делённое на среднее. На границах 15% и 30% сравниваются точные квадраты, без влияния округления квадратного корня. Среднее для падения оборота использует **12** месяцев, для баллов/дохода — **6**; эти окна не подменяют друг друга.

Итог: `<500` — красная полоса; `500–649` — серая; `650–850` — зелёная. Все реальные суммы факторов V1 кратны 10; граничные тесты 499/500/649/650/850 отдельно проверяют классификатор полос. Низкий балл не означает измеренную вероятность дефолта.

Ставка для зелёной полосы — 16,5% годовых; для остальных расчётных полос — 18,5%. Зелёная заявка, переданная сотруднику из-за мягкого предупреждения, сохраняет 16,5%. Диапазон 18,5–21% в wiki не задаёт алгоритма выбора; V1 явно выбирает одну настройку 18,5%. Конфигурация допускает 0–100% с максимум четырьмя десятичными знаками; это предел численного интерфейса, а не рекомендация ставки.

## Доступность и округления

Обозначения: `T` — средний чистый оборот за 6 месяцев; `Y = 0.35 × T` — учебный доход; `B` — имеющийся месячный долг; `A` — сумма; `n` — месяцы; `i = annualRatePercent / 1200`.

```text
payment(A) = A × i × (1+i)^n / ((1+i)^n − 1)
при i = 0: payment(A) = A / n
ratio = (B + payment(A)) / Y
availableMonthlyPayment = 0.50 × Y − B
```

Процентные вычисления используют `MathContext.DECIMAL128`. Ежемесячный платёж округляется **вверх до копейки**. Границы доли платежей сравниваются через умножение исходных сумм, без округления отношения до процентов. `requestedDebtRatio` и `TermsEvaluation.debtRatio` возвращаются **долями единицы**: `0.45` означает 45%. Для `ScoreFactor.value` коэффициент вариации тоже представлен долей.

Для контр-оффера решается обратная аннуитетная формула с тем же сроком и ставкой. Месячный бюджет округляется вниз до копейки. Максимум ограничивается запросом и продуктом, затем округляется **вниз до целого рубля** для совместимости с исходным `int64` API. Полученный платёж рассчитывается повторно. Если численная граница не проходит проверку, применяется ограниченный двоичный поиск по целым рублям; нет неограниченного цикла уменьшений.

При неположительном бюджете лимит равен нулю. Лимит ниже 100 000 ₽ не становится предложением. Для положительного бюджета нулевая ставка имеет отдельную формулу `maxAmount = budget × n`. Предложение никогда не превышает запрос, а уменьшенная сумма не маскирует жёсткий стоп, красную полосу или неполные данные.

DSCR, стресс-сценарии, расширенные финансовые модели, документы, подпись/выдача и смежные интеграции в минимальный движок не входят. Это сознательная граница рабочего хакатонного прототипа.

## Повторная проверка сотрудником и клиентское согласие

`Assessment.evidenceComplete` означает, что для расчёта достаточно корректных применимых входов; жёсткий стоп может вернуть этот признак `true`, но балл не вычисляется. `eligibleForManualApproval` дополнительно требует отсутствия жёстких стопов/красной полосы и доступного минимума продукта. Даже `true` не является разрешением выполнить запись: сервис обязан вызвать `evaluateTerms` и проверить состояние/версию в транзакции.

Сотрудник может разрешить серую полосу или мягкий флаг с обязательным обоснованием. Он не может обойти неполные/устаревшие входы, жёсткий стоп, красную полосу, лимит платежей, минимум продукта или ограничение суммы запросом. При неполных данных `score`, лимит и условия остаются `null`; такие заявки можно изучить и отклонить, но не одобрить без отдельного предусмотренного обновления данных.

Сервисные переходы: `PROCESSING → APPROVED | REJECTED | MANUAL_REVIEW | OFFER_PROPOSED`; сотрудник решает только из `MANUAL_REVIEW`; владелец принимает или отклоняет предложение только из `OFFER_PROPOSED`. Терминальные `APPROVED`/`REJECTED` в ядре не редактируются. `APPROVED` в этой системе — завершение учебного сценария, а не выдача кредита.

## Проверки

`RiskEngineTest` проверяет границы 499/500/649/650/850, 6 месяцев, 59/60 дней, 90/91 дней, падение 35%, доли 45/50%, все факторные границы, нули/пропуски/устаревшие/отрицательные признаки, неизменяемость, повторяемость, нулевую ставку, округление, пределы контр-оффера и запрет обхода через сотрудника. Тесты используют реальные классы без mock-движка.

Из каталога `backend` с установленной Java 25:

```bash
bash gradlew test --tests 'ru.alfahackaton.risk.RiskEngineTest'
```

Фактические результаты выполнения, версии инструментов и ограничения среды находятся в общем `VERIFICATION.md` поставки. Проверки этого чистого модуля не заменяют PostgreSQL-тесты транзакций, восстановление worker, RBAC и реальный fullstack через Nginx.
