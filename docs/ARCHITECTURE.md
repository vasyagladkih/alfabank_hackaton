# Архитектура решения: Умный кредитный кабинет ММБ

## 1. Назначение системы

Система представляет собой цифровой кредитный конвейер малого и микробизнеса (ММБ) для автоматизации процесса кредитования: от подачи заявки предпринимателем до проверки стоп-факторов, скоринга, вынесения решения и внутрипродуктового подписания кредитного договора.

Система обслуживает две ключевые роли:
* **Клиент (Предприниматель / ЮЛ / ИП):** подача заявки, мгновенная обратная связь со статусом обработки, просмотр персонализированного аннуитетного графика платежей и подписание кредитной документации (ПЭП).
* **Сотрудник банка (Андеррайтер / Риск-офицер):** мониторинг реестра заявок с серверной пагинацией и фильтрами, детальный аудит досье заемщика (сырые снимки ФНС и БКИ, скоринг-баллы, ПДН) и возможность ручного перезапуска конвейера при аппаратных сбоях внешних реестров.

## 2. Архитектурная топология компонентов

Архитектура решения построена по принципу модульного монолита с четким разделением слоев ответственности и использованием реактивно-асинхронных паттернов для сетевых интеграций.

| Компонент / Слой | Технологический стек | Назначение и зона ответственности |
| :--- | :--- | :--- |
| **Client UI (Фронтенд)** | React, TypeScript, Alfa Core Components | Веб-интерфейс заемщика и сотрудника бэк-офиса. Работает строго через REST API по OpenAPI-контракту. |
| **API Gateway / Security** | Spring Security 6, OAuth 2.0 Resource Server | Аутентификация через асимметричный JWT (RS256), авторизация на базе ролей (RBAC), защита от IDOR. |
| **Application Layer** | Spring Boot 4, Java 25 | Бизнес-логика конвейера, оркестрация скоринга, генерация аннуитетных графиков, управление жизненным циклом. |
| **Decision Engine** | Core Java (детерминированный движок) | 4-этапный скоринг: законодательные стоп-факторы, расчет ПДН, лимитов выручки и индивидуальной ставки. |
| **Persistence Layer** | Spring Data JDBC, PostgreSQL 16 | Реляционное хранилище данных: пользователи, заявки и неизменяемые аудиторские снимки внешних систем. |
| **Integration Stubs** | Spring MVC, изолированные таблицы БД | Автономные эмуляторы государственных и кредитных реестров (ФНС, БКИ) на синтетических данных. |

## 3. Асинхронный событийный конвейер (Event-Driven Pipeline)

Процесс обработки кредитной заявки разделен на синхронную регистрацию и асинхронную оркестрацию. Это гарантирует быстрый Time-to-Response для клиента (менее 50 мс) и предотвращает исчерпание пула соединений к базе данных.

### Схема прохождения заявки по этапам:

1. **Регистрация заявки (Синхронно):**
   * Клиент отправляет запрос `POST /api/v1/client/applications`.
   * Метод `ApplicationService.createApplication` выполняется в транзакции: проверяет существование пользователя, сохраняет запись заявки в статусе `PROCESSING` в PostgreSQL.
   * Публикуется внутреннее событие `ApplicationCreatedEvent`.
   * Метод коммитит транзакцию и возвращает клиенту ответ HTTP 201 Created с присвоенным `id` и статусом `PROCESSING`.

2. **Защита от состояния гонки (Race Condition):**
   * Обработчик события `ApplicationEventListener.onApplicationCreated` аннотирован:
     `@Async` и `@TransactionalEventListener(phase = TransactionPhase.AFTER_COMMIT)`.
   * **Критический инвариант:** асинхронная задача скоринга стартует в отдельном виртуальном потоке **только после физического коммита** записи заявки в PostgreSQL. Это исключает ошибку `EntityNotFoundException` при чтении заявки из фонового потока.

3. **Параллельное обогащение (Enrichment):**
   * Фоновый метод `ApplicationService.processApplication` извлекает базовые параметры компании и запускает параллельный опрос сервисов-партнеров через `CompletableFuture.supplyAsync()` на виртуальных потоках:
     * Поток 1: `FnsEnrichmentService.enrich()` $\rightarrow$ опрос реестра ФНС.
     * Поток 2: `BkiEnrichmentService.enrich()` $\rightarrow$ опрос бюро кредитных историй.
   * Установлен жесткий таймаут: `.orTimeout(1500, TimeUnit.MILLISECONDS)`.

4. **Вынесение решения (Decisioning):**
   * Результаты опроса объединяются в объект `BorrowerDossier`.
   * `DecisionEngine.evaluate(dossier)` производит расчет скоринга в памяти JVM без обращений к базе данных.

5. **Фиксация решения в БД:**
   * Вызов `applicationRepository.updateDecision(...)` атомарно сохраняет решение, рассчитанную ставку, лимит, ПДН и новый статус в PostgreSQL.

6. **Самовосстановление зависших заявок (Startup Recovery):**
   * При перезапуске сервиса (рестарт пода, OOM, Rolling Update) слушатель `ApplicationReadyEvent` находит в базе данных PostgreSQL все заявки, оставшиеся в незавершенном статусе `PROCESSING`, и передает их в `processApplication(id)` для асинхронного возобновления конвейера.

## 4. Меры отказоустойчивости (Fault Tolerance & Resilience)

В конвейере реализован комплекс защитных механизмов, предотвращающих каскадные сбои при деградации внешних систем:

1. **Изоляция сетевых вызовов от транзакций БД (Защита от Connection Starvation):**
   * Метод `processApplication` выполняется **без аннотации `@Transactional`**.
   * Пока подпотоки ожидают сетевого ответа от ФНС и БКИ (до 1.5 секунд), физические соединения из пула HikariCP **не удерживаются**.
   * Запись каждого снимка (`fnsSnapshotRepository.save`, `bkiSnapshotRepository.save`) выполняется в собственной микро-транзакции, занимающей менее 2 мс.

2. **Безопасная деградация (Graceful Degradation):**
   * Ошибки сокетов, HTTP 5xx и таймауты перехватываются блоком `.exceptionally()`, логируются и возвращают `null` вместо прерывания процесса исключением.
   * Если хотя бы один реестр недоступен, конвейер переводит заявку в статус `MANUAL_REVIEW` с бизнес-кодом `TECH_FAILURE`.
   * Если ФНС ответила успешно, а БКИ сбоит, снимок ФНС уже зафиксирован в базе и доступен андеррайтеру.

3. **Механизм контролируемого повтора (Retry Mechanism):**
   * Для заявок со статусом `MANUAL_REVIEW` и кодом `TECH_FAILURE` система рассчитывает флаг `canRetry = true`.
   * Эндпоинт `POST /api/v1/employee/applications/{id}/retry` переводит заявку обратно в статус `PROCESSING` и запускает конвейер заново без необходимости для заемщика создавать новую заявку.

4. **Низкоуровневые таймауты сокетов:**
   * В клиентах `FnsClientService` и `BkiClientService` настроены таймауты сетевого подключения `ConnectTimeout = 1000 мс` и чтения `ReadTimeout = 1000 мс` (`SimpleClientHttpRequestFactory`).

5. **Архитектурный паттерн самовосстановления конвейера (Startup Recovery):**
   * **Проблема:** При аварийном завершении работы приложения (OutOfMemory, SIGKILL, Rolling Update подов в Kubernetes или сбой питания сервера) заявки, находившиеся в фазе параллельного сетевого обогащения, могли зависнуть в базе данных PostgreSQL в промежуточном статусе `PROCESSING`.
   * **Механизм восстановления:** Слушатель события `ApplicationReadyEvent` активируется в момент полной инициализации контекста Spring Boot, когда все пулы соединений (HikariCP), репозитории и диспетчеры виртуальных потоков готовы к работе.
   * **Алгоритм работы:**
     1. Слушатель выполняет выборку всех заявок со статусом `PROCESSING` из базы данных PostgreSQL (`SELECT id FROM applications WHERE status = 'PROCESSING' ORDER BY created_at ASC`).
     2. Для каждой зависшей заявки логируется факт возобновления скоринга.
     3. Асинхронно вызывается оркестратор конвейера `applicationService.processApplication(id)`.
     4. Благодаря идемпотентности конвейера и изоляции снимков (`fns_snapshots`, `bki_snapshots`) заявка дообогащается и гарантированно переводится в целевой статус (`APPROVED`, `MANUAL_REVIEW` или `REJECTED`), исключая «потерянные» бизнес-транзакции.

## 5. Транзакционная модель базы данных

| Слой / Операция | Управление транзакцией | Поведение при отказе |
| :--- | :--- | :--- |
| **`createApplication`** | `@Transactional` (Spring declarative) | Rollback при ошибке валидации; заявка не создается, событие не публикуется. |
| **`processApplication`** | Non-transactional (Оркестратор) | Не блокирует соединения БД при сетевых вызовах. |
| **`StartupRecovery`** | Non-transactional (Read + Async) | Поиск зависших заявок в статусе `PROCESSING` по `ApplicationReadyEvent` и их повторный запуск. |
| **`FnsEnrichmentService.save`** | Атомарный `save()` Spring Data | При сетевом сбое транзакция БД даже не открывается. |
| **`BkiEnrichmentService.save`** | Атомарный `save()` Spring Data | Изолирована от ФНС; сбой в БКИ не отменяет снимок ФНС. |
| **`updateDecision`** | `@Modifying @Transactional` | Атомарный `UPDATE` заявки в PostgreSQL с обновлением `updated_at`. |
| **`approveApplication`** | `@Transactional` | Атомарный переход `MANUAL_REVIEW` $\rightarrow$ `APPROVED`, фиксация лимита/ставки и комментария андеррайтера. |
| **`rejectApplication`** | `@Transactional` | Атомарный переход `MANUAL_REVIEW` $\rightarrow$ `REJECTED`, фиксация мотивированной причины отказа. |
| **`signApplication`** | `@Transactional` | Атомарный переход `APPROVED` $\rightarrow$ `SIGNED` с валидацией условий. |

## 6. Конечный автомат заявки (State Machine)

Жизненный цикл заявки описывается детерминированным конечным автоматом. Любые несанкционированные переходы блокируются бизнес-логикой сервиса.

| Исходный статус | Целевой статус | Триггер / Условие перехода |
| :--- | :--- | :--- |
| *Отсутствует* | `PROCESSING` | Вызов `POST /api/v1/client/applications`. Заявка сохранена в БД, скоринг инициирован. |
| `PROCESSING` | `APPROVED` | Пройдены все стоп-факторы, скоринг-балл $\ge 65$, ПДН $\le 80\%$, лимит $\ge 100\,000$ ₽. |
| `PROCESSING` | `REJECTED` | Сработал стоп-фактор (банкротство, ст. 76 НК РФ, дефолт 90+ DPD) либо балл $< 50$ / ПДН $> 80\%$. |
| `PROCESSING` | `MANUAL_REVIEW` | Технический сбой внешнего сервиса (`TECH_FAILURE`) либо пограничный балл 50–64 (`BORDERLINE_SCORE`). |
| `PROCESSING` | `PROCESSING` | Самовосстановление при рестарте приложения (`ApplicationReadyEvent` возобновляет скоринг). |
| `MANUAL_REVIEW` | `PROCESSING` | Сотрудник банка нажал кнопку перезапуска `POST /api/v1/employee/applications/{id}/retry`. |
| `MANUAL_REVIEW` | `APPROVED` | Ручное одобрение андеррайтером: `POST /api/v1/employee/applications/{id}/approve` с фиксацией лимита/ставки. |
| `MANUAL_REVIEW` | `REJECTED` | Ручной отказ андеррайтера: `POST /api/v1/employee/applications/{id}/reject` с фиксацией причины отказа. |
| `APPROVED` | `SIGNED` | Заемщик подтвердил согласие с условиями: `POST /api/v1/client/applications/{id}/sign`. |

**Инвариант неизменяемости:** Статусы `REJECTED` и `SIGNED` являются терминальными (конечными) состояниями. Повторное изменение условий по ним запрещено.

## 7. Модель безопасности

1. **OAuth 2.0 Resource Server:**
   * Сервис работает в режиме Stateless Resource Server.
   * Подлинность токенов проверяется декодером `NimbusJwtDecoder` по открытому RSA-ключу (`RSAPublicKey`). Приватный ключ для выпуска токенов хранится в защищенном контуре IdP (в рамках хакатона смоделирован в `AuthService`).
2. **Ролевой доступ (RBAC):**
   * Роль `CLIENT`: доступ только к подаче, просмотру и подписанию собственных заявок (`/api/v1/client/**`).
   * Роль `EMPLOYEE`: доступ к пагинированному реестру всех заявок компании, просмотру кредитного досье и вызову перезапуска (`/api/v1/employee/**`).
3. **Защита от горизонтальной эскалации привилегий (IDOR):**
   * Все запросы клиента фильтруются предикатом `WHERE id = :applicationId AND user_id = :currentUserId`.
   * Попытка заемщика обратиться к заявке другого клиента возвращает ошибку `404 Not Found`.
