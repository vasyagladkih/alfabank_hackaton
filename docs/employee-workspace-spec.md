# Рабочее место сотрудника: согласованный demo-контракт

Статус этого документа: **спецификация пакета issue-15**, реализация — следующий пакет issue-18. Это предложенное разделение почти пустых issue-15/18, а не приписанные им исходные acceptance criteria. Основой служат работающий API проекта, `data-dictionary.md`, `risk-policy.md` и приложенный implementation brief. Командная wiki (`43940dea4636beebb909a66c0e005c7f72b5e768`) — ориентир, не официальная спецификация кейса.

## 1. Назначение

Сотрудник открывает очередь синтетических заявок, понимает, какие входы и правила привели к учебной рекомендации, и принимает обоснованное demo-решение для заявки на ручном рассмотрении. Клиент видит изменение и может принять или отклонить встречное предложение. Никаких реальных договоров, выдачи, запросов в ФНС/БКИ или оценки реальных компаний нет. Цвет статуса всегда сопровождается текстом; источник явно помечен «Демо».

Сохраняются React 17, официальные Alfa Core Components, существующие маршруты `/login`, `/client`, `/employee`, `/403`, `PROCESSING`, ограничения 100 000–50 000 000 целых рублей / 1–60 месяцев, RBAC, polling и восстановление клиентских баннеров.

## 2. Экран и источники полей

| Блок | Поля интерфейса | Источник / правила отсутствия |
|---|---|---|
| Очередь | №, компания, ИНН, сумма, срок, цель, статус, дата, версия | `applications` + существующий `users`; запрос сохраняется отдельно от предложенной суммы |
| Поиск и фильтр | Поиск по №/компании/ИНН, все пять статусов, «Все», обновление | `GET /employee/applications?status=&search=`; search ≤120 символов; отсутствие status сохраняет фактическое поведение — все заявки |
| Карточка | Данные запроса, текущий статус, версия, доступные действия | `EmployeeDossier.application`, `allowedActions`; сервер определяет действия, UI не принимает решение по одному цвету/баллу |
| Профиль | Регистрация, открытие счёта, изменения руководства, полнота истории | Неизменяемый `application_snapshots.inputs`, полученный от FNS/internal mock providers; неизвестное — «Нет данных», не 0/false |
| Финансы | 12 закрытых месяцев оборота, месячный долг, учебный доход, платёж, доля платежей, доступная сумма | Снимок internal/BKI + сохранённый `scoring_results`; RUB, `debtRatio` — доля 0.45=45%; среднее дохода за 6 месяцев, падение оборота за 12 |
| Проверки | Синтетический балл БКИ, 24-месячная просрочка, 12-месячная закрытая просрочка, блокировка/банкротство/ликвидация | BKI/FNS mock snapshot; это отдельные исходные факты, не результат live-запроса |
| Источники | Название, версия, дата, свежесть FRESH/STALE/MISSING/INVALID | `sources[]`; FNS/BKI ≤30 дней, internal ≤45, относительно сохранённого `snapshotAsOf`, не текущих часов браузера |
| Объяснение | Итоговый балл из 850, четыре фактора, максимум и вклад, причины/коды, версия правил | Сохранённый `assessment`; hard stop и неполные входы могут не иметь балла — показывается объяснение без выдуманного 0 |
| Снимок | Дата оценки, время сохранения, происхождение, SHA-256 | `application_snapshots`; обновление экрана перечитывает данные, не перезаписывает snapshot |
| Аудит | Время, роль, тип события, переход, rationale, версия | Append-only `application_audit`; доступен сотруднику, не содержит JWT или финансовых данных реальных лиц |

Для старой завершённой заявки без snapshot/assessment экран честно сообщает об отсутствии расчётных данных. Для старой `PROCESSING` восстановление фиксирует новый снимок с явным происхождением `LEGACY_RECOVERY`; оно не выдаётся за исходный исторический снимок. Несколько сценариев могут принадлежать одному из прежних трёх demo-профилей — login enum не расширяется.

## 3. Контракты

Активный контракт после issue-16: `docs/openapi.yaml`. Точное аддитивное расширение для issue-18: [`contracts/employee-api-extension.yaml`](contracts/employee-api-extension.yaml). В issue-15 оно оставлено отдельным файлом, чтобы не генерировать обязательные Spring-методы до их реализации. В issue-18 эти определения объединяются с активным OpenAPI и одновременно генерируются Java/TypeScript-потребители.

| Операция | Вход | Результат |
|---|---|---|
| `GET /api/v1/employee/applications` | optional `status`, `search` | Очередь `ApplicationResponse[]`, совместимый базовый endpoint |
| `GET /api/v1/employee/applications/{id}` | id | `EmployeeDossier`: application, facts, cashflows, sources, assessment, allowedActions, audit, snapshot metadata |
| `POST /api/v1/employee/applications/{id}/decisions` | `expectedVersion`, UUID `requestId`, `type=APPROVE/REJECT/COUNTEROFFER`, `rationale` 3–1000 непустых символов; `offerAmount` только для COUNTEROFFER | Полное обновлённое досье; сумма предложения — целые RUB; срок/ставка не изменяются |
| `POST /api/v1/client/applications/{id}/offer-response` | `expectedVersion`, UUID `requestId`, `decision=ACCEPT/REJECT` | Обновлённый `ApplicationResponse`; только владелец |

Денежные расчёты/ставки в ответах — десятичные строки; суммы исходной заявки/предложения — int64 RUB. Источники, названия фактов и причины — серверные поля с понятными метками. `demoOnly=true` обязателен в досье и кратком решении. Клиент получает краткое объяснение и условия; employee dossier не доступен клиенту.

## 4. Переходы и ограничения

| Исходный статус | Актор / действие | Следующий статус | Проверка |
|---|---|---|---|
| — | Клиент / создать | PROCESSING | Собственный профиль, валидный запрос; snapshot + job + CREATED в одной транзакции |
| PROCESSING | Worker / правила | APPROVED, REJECTED, MANUAL_REVIEW или OFFER_PROPOSED | Один сохранённый snapshot/версия правил; результат, версия, audit и завершение job атомарны |
| MANUAL_REVIEW | Сотрудник / APPROVE | APPROVED | Полные/применимые данные, нет hard stop/красной полосы, исходные условия проходят `evaluateTerms`; rationale обязателен |
| MANUAL_REVIEW | Сотрудник / REJECT | REJECTED | Rationale обязателен, в том числе при недостаточных данных |
| MANUAL_REVIEW | Сотрудник / COUNTEROFFER | OFFER_PROPOSED | Допустимый минимум ≤ offerAmount ≤ request и доступный лимит; тот же срок/ставка, `evaluateTerms` повторно |
| OFFER_PROPOSED | Клиент-владелец / ACCEPT | APPROVED | Актуальная версия и сохранённое действительное предложение; это demo-согласие без договора |
| OFFER_PROPOSED | Клиент-владелец / REJECT | REJECTED | Отдельное событие отказа клиента; не приписывается отрицательному скорингу |
| APPROVED / REJECTED | Любой | Без изменения | Терминальные статусы нельзя произвольно пересмотреть этим API |

Приоритет правил: свежий подтверждённый hard stop → качество данных → низкий балл → серая полоса/soft stop → доступность. Пороги 50%, 35%, ставки и scorecard — настраиваемые учебные допущения, не регуляторные требования. Оценка не является PD, NPL или CoR. Границы и округления находятся в `risk-policy.md`.

При неполных/устаревших входах UI показывает только разрешённые сервером действия; сотрудник не может «одобрить несмотря ни на что». Исправление/повторный сбор исходных данных и новая версия snapshot — будущая отдельная операция, не скрытое действие кнопки «Обновить».

## 5. RBAC, повторы и конфликты

Гость/некорректный JWT получает 401. Клиенту employee API недоступен (403); сотруднику клиентские операции недоступны (403). Клиентский detail/offer проверяет владельца на сервере; чужая существующая заявка — 403, отсутствующая — 404. Клиент не передаёт owner id для смены владельца. Employee search выполняется параметризованным запросом.

Команда выполняется транзакционно с блокировкой заявки. После проверки доступа ищется точный повтор `(applicationId, actorUserId, requestId)`: тот же endpoint/payload возвращает сохранённый результат 200 и не создаёт аудит повторно. Другой payload под тем же ключом в этой заявке — 409. UUID ограничен заявкой и пользователем; такой же UUID в другой заявке — отдельная команда. Новая команда требует совпадения `expectedVersion` и разрешённого исходного статуса; иначе 409. Два одновременных разных решения одной версии дают один успех и один 409. Изменение, аудит и запись результата повтора коммитятся вместе.

На 409 интерфейс сохраняет введённую причину и желаемую сумму, перечитывает досье и объясняет конфликт. Автоматически не отправляет сохранённое намерение заново. Повтор сетевого запроса без изменения формы использует тот же UUID; изменённая команда получает новый UUID. На 401 очищается сессия; на 403 сохраняется корректная сессия и открывается существующий экран доступа. На 500 показывается безопасная ошибка с повтором загрузки.

## 6. UI и матрица приёмки

Очередь и досье остаются внутри `/employee`; выбор заявки доступен клавиатурой и имеет понятное название. Alfa Button/Input/Status/Plate/Table/Typography сохраняют корпоративную тему; native select обёрнут в Core FormControl согласно существующей доступной композиции. Фокус переводится к открытой карточке/ошибке осмысленно. Нет декоративных эффектов и зависимости понимания от цвета.

| Требование | API / состояние | Проверка |
|---|---|---|
| Сценарий ручного решения | queue→dossier→decision→client detail | Реальный HTTP/Nginx/PostgreSQL, новая версия и audit; отдельно approve/reject |
| Предложение | employee COUNTEROFFER + client ACCEPT/REJECT | Предложение ≤ request, состояние синхронизируется у обоих ролей; исходная сумма не потеряна |
| Неизвестные/устаревшие данные | assessment/sources + allowedActions | Нет выдуманных чисел/ложной свежести, запрещено обходное одобрение |
| RBAC/IDOR/404 | все endpoints | 401/403/404 на реальном сервере; клиент не читает employee dossier |
| Конкурентность | decisions / offer-response | Одна версия: один 200, один 409; audit один; полный rollback при ошибке |
| Безопасный повтор | тот же requestId | Replay после потери ответа не дублирует события; изменённый payload 409 |
| Перезапуск | PROCESSING/job | Завершение после перезапуска по сохранённым входам, без повторного результата/audit |
| Polling/баннеры | MANUAL_REVIEW/OFFER_PROPOSED до terminal | Обновление/восстановление страницы, logout/abort; регрессии PR13 сохранены |
| Контракт | OpenAPI ↔ TS ↔ Spring | generation/drift, runtime validation статусов/версий/денег |
| Доступность | login/client/employee/dossier/403 | 320/390/768/1440, без горизонтального переполнения страницы; клавиатура, axe serious/critical без отключения правил |
| Формы/сбои | rationale/amount/409/500/loading | Ошибки связаны с полями, ввод не теряется при конфликте, повтор явный |

Fixture-тесты браузера проверяют UI-состояния; отдельные real-stack тесты обязаны выполнять запросы к настоящему backend через Nginx без перехвата транспорта. Отчёт сборки отличает выполненные проверки от описанной этой спецификацией матрицы.

## 7. За пределами этого пакета

Полный калькулятор, договор/PDF/CSV, подпись/выдача, портфельная аналитика, новости и ML не входят в реализацию. FNS/BKI/internal finance — детерминированные mock providers с явными Java-контрактами. Будущий адаптер банка может заменить реализацию провайдера, сохраняя единицы, missingness, источники и snapshot, но подключение реальных данных здесь не реализуется и не имитируется как состоявшееся.
