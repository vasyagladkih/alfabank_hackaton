# Сценарии проверки и E2E Walk-Through

Данный документ содержит пошаговую инструкцию для экспертов жюри Альфа-Банка по проверке ключевых сценариев цифрового кредитного конвейера ММБ как через графический веб-интерфейс, так и через прямые вызовы REST API (cURL / PowerShell).

---

## 1. Подготовка и запуск окружения

### Вариант А: Запуск в Docker (Рекомендуемый)
В корне проекта выполните одну команду:
```bash
docker compose up --build
```
* **Клиентский веб-кабинет:** `http://localhost:3000`
* **Бэкенд REST API:** `http://localhost:8080`

### Вариант Б: Локальный запуск
1. Запуск PostgreSQL (порт 5432, база `alfadb`, логин/пароль `postgres/postgres`).
2. Запуск бэкенда:
   ```bash
   cd backend
   ./gradlew bootRun
   ```
3. Запуск фронтенда:
   ```bash
   cd frontend
   npm ci
   npm run dev
   ```

## 3. Сценарий 1: Сквозное автоматическое одобрение и выдача (Happy Path)

Демонстрирует путь надежного предпринимателя от подачи заявки до автоматического одобрения за 2 секунды и подписания кредитного договора.

### Шаги прохождения:
1. **Авторизация:**
   * В интерфейсе на экране демо-входа выберите **«client_good (ООО "Ромашка")»**.
   * Нажмите кнопку «Войти».
2. **Подача кредитной заявки:**
   * В кабинете клиента нажмите «Новая заявка».
   * Укажите параметры:
     * **Сумма:** `2 500 000` ₽
     * **Срок:** `24` месяца
     * **Цель:** `Пополнение оборотных средств`
   * Нажмите «Отправить заявку».
3. **Обработка конвейером:**
   * Заявка мгновенно регистрируется со статусом `PROCESSING`.
   * Бэкенд асинхронно параллельно опрашивает ФНС и БКИ.
   * Спустя 1.5 секунды статус автоматически меняется на `APPROVED` (Одобрено).
4. **Просмотр условий и графика платежей:**
   * В карточке заявки отображаются рассчитанные условия:
     * Одобренная ставка: `17.5%` годовых (пониженная за счет высокого скоринг-балла).
     * Ежемесячный аннуитетный платеж.
     * Полный график платежей с детализацией основного долга и процентов со сходимостью остатка в 0 руб.
5. **Подписание договора (ПЭП):**
   * Ознакомьтесь с условиями и отметьте чекбокс согласия.
   * Введите смоделированный код подтверждения (например, `1234`) и нажмите «Подписать договор».
6. **Результат:**
   * Заявка переходит в статус **`SIGNED`** (Кредит оформлен).

## 4. Сценарий 2: Законодательный отказ по стоп-факторам (Stop Factors)

Демонстрирует строгое соблюдение требований законодательства (ст. 76 НК РФ, 218-ФЗ) и отсечение высокорисковых заемщиков без ручного труда андеррайтера.

### Шаги прохождения:
1. **Авторизация:**
   * Выйдите из профиля и войдите под **`client_bad (ООО "Однодневка")`**.
2. **Подача заявки:**
   * Создайте заявку на любую сумму (например, `1 000 000` ₽ на `12` месяцев).
3. **Отработка риск-модели:**
   * Конвейер выявляет критические стоп-факторы:
     * В ФНС: статус `BANKRUPT` и действующие блокировки банковских счетов по ст. 76 НК РФ.
     * В БКИ: наличие 2 исторических дефолтов свыше 90 дней (`cntOverdueOver90d = 2`).
4. **Результат:**
   * Заявка мгновенно переходит в статус **`REJECTED`**.
   * Клиент видит юридически аргументированную причину отказа: *«Отказ: организация находится в процедуре банкротства или ликвидации; действующие блокировки счетов»*.

## 5. Сценарий 3: Рабочее место андеррайтера — аудит досье, принятие решения и подписание клиентом

Демонстрирует полный цикл ручной обработки заявок в статусе `MANUAL_REVIEW`: аудит досье, ручное одобрение со сменой условий, мотивированный отказ, обработку технических сбоев (`TECH_FAILURE`) и последующее подписание клиентом кредитного договора.

### 5.1. Ручной андеррайтинг: аудит досье, одобрение и подписание клиентом
1. **Появление заявки на ручном рассмотрении:**
   * Заявка заемщика переведена в статус `MANUAL_REVIEW` (пограничный скоринг-балл, встречное предложение/контр-оффер или ссуда III категории качества по 590-П).
2. **Вход андеррайтера:**
   * В интерфейсе демо-входа выберите профиль **«bank_employee (АО "АЛЬФА-БАНК")»**.
3. **Работа с реестром заявок:**
   * Открывается реестр заявок с серверной пагинацией и фильтрами по статусам.
   * Андеррайтер находит заявку со статусом `MANUAL_REVIEW` и кодом `BORDERLINE_SCORE` (флаг `canRetry = false`).
4. **Аудит кредитного досье заемщика:**
   * При клике на заявку загружается детальное кредитное досье (`GET /api/v1/employee/applications/{id}`):
     * Параметры запроса (сумма, срок, цель финансирования).
     * Финансовые показатели из РКО (годовой и среднемесячный оборот компании).
     * Верифицированные данные ФНС (активный статус юрлица, отсутствие арестов по ст. 76 НК РФ).
     * Отчет БКИ (скоринговый балл бюро, платежная дисциплина, текущие ежемесячные платежи).
     * Расчетные метрики конвейера (скоринг-балл, расчетный ПДН, максимально допустимый безопасный лимит).
5. **Принятие решения андеррайтером:**
   * **Ветка А — Ручное одобрение:**
     * Андеррайтер в панели управления досье нажимает кнопку «Одобрить заявку».
     * При необходимости фиксирует или корректирует условия (например, сумму `1 500 000` ₽ и процентную ставку `18.5%`).
     * Вводит обязательный мотивированный комментарий (например: *«Обороты подтверждены выписками РКО, долговая нагрузка группы умеренная»*).
     * Отправляет решение вызовом `POST /api/v1/employee/applications/{id}/approve`.
     * Статус заявки меняется на **`APPROVED`**, система генерирует актуальный аннуитетный график платежей со сходимостью в 0 руб.
   * **Ветка Б — Мотивированный отказ:**
     * В случае выявления скрытых рисков андеррайтер нажимает кнопку «Отклонить заявку».
     * Заполняет развернутое обоснование отказа (например: *«Высокая совокупная долговая нагрузка группы связанных лиц»*).
     * Отправляет решение вызовом `POST /api/v1/employee/applications/{id}/reject`.
     * Статус заявки переходит в **`REJECTED`** с фиксацией комментария в поле `rejection_reason`.
6. **Подписание договора клиентом (по одобренной заявке):**
   * Клиент заходит в личный кабинет под своим профилем (например, **`client_good`**).
   * В карточке заявки отображаются одобренные андеррайтером условия, ставка и полный аннуитетный график.
   * Клиент ставит отметку согласия с условиями кредитования и вводит SMS-код простой электронной подписи (ПЭП) через `POST /api/v1/client/applications/{id}/sign`.
   * Заявка переходит в терминальный статус **`SIGNED`** (Кредит оформлен, договор подписан).

### 5.2. Обработка технического сбоя внешних реестров (TECH_FAILURE) и перезапуск (Retry)
1. **Моделирование сбоя:**
   * При таймауте (1500 мс) или сетевой ошибке шлюза ФНС/БКИ конвейер изолирует ошибку, переводит заявку в статус `MANUAL_REVIEW` с причиной `TECH_FAILURE` и рассчитывает флаг `canRetry = true`.
2. **Аудит сбоя андеррайтером:**
   * В кредитном досье андеррайтер видит, какой именно шлюз не ответил, при этом успешно полученные снимки зафиксированы в БД.
3. **Перезапуск конвейера (Retry):**
   * Андеррайтер нажимает активную кнопку **«Перезапустить скоринг»** (`POST /api/v1/employee/applications/{id}/retry`).
   * Заявка возвращается в статус `PROCESSING`, система повторно опрашивает упавшие внешние сервисы и автоматически выносит итоговое решение.

## 6. Автоматизированная проверка через консоль (cURL)

Эксперты могут проверить полную сквозную функциональность бэкенда через терминал без открытия браузера.

### 1. Получение JWT-токенов клиентов и сотрудника:
```bash
# Токен заемщика
CLIENT_TOKEN=$(curl -s -X POST http://localhost:8080/api/v1/auth/demo-login \
  -H "Content-Type: application/json" \
  -d '{"username":"client_good"}' | grep -o '"token":"[^"]*' | cut -d'"' -f4)

# Токен сотрудника банка (андеррайтера)
EMPLOYEE_TOKEN=$(curl -s -X POST http://localhost:8080/api/v1/auth/demo-login \
  -H "Content-Type: application/json" \
  -d '{"username":"bank_employee"}' | grep -o '"token":"[^"]*' | cut -d'"' -f4)
```

### 2. Создание заявки клиентом:
```bash
APP_ID=$(curl -s -X POST http://localhost:8080/api/v1/client/applications \
  -H "Authorization: Bearer $CLIENT_TOKEN" \
  -H "Content-Type: application/json" \
  -d '{"amount":2500000,"termMonths":24,"purpose":"REPLENISHMENT_WORKING_CAPITAL"}' \
  | grep -o '"id":[0-9]*' | head -1 | cut -d':' -f2)

echo "Создана заявка #$APP_ID"
```

### 3. Просмотр детального досье андеррайтером:
```bash
curl -s -X GET "http://localhost:8080/api/v1/employee/applications/$APP_ID" \
  -H "Authorization: Bearer $EMPLOYEE_TOKEN"
```

### 4. Сценарий ручного одобрения андеррайтером (Approve):
```bash
# Андеррайтер одобряет заявку с корректировкой лимита, ставки и мотивированным комментарием
curl -s -X POST "http://localhost:8080/api/v1/employee/applications/$APP_ID/approve" \
  -H "Authorization: Bearer $EMPLOYEE_TOKEN" \
  -H "Content-Type: application/json" \
  -d '{
    "approvedAmount": 1500000,
    "approvedRate": 18.5,
    "comment": "Обороты устойчивы, предоставлены договоры с контрагентами"
  }'
```
*(Статус меняется на `APPROVED`, сформирован аннуитетный график).*

### 5. Подписание договора клиентом по SMS-коду (Sign):
```bash
# Клиент подтверждает условия и вводит SMS-код ПЭП
curl -s -X POST "http://localhost:8080/api/v1/client/applications/$APP_ID/sign" \
  -H "Authorization: Bearer $CLIENT_TOKEN" \
  -H "Content-Type: application/json" \
  -d '{"confirmTerms":true,"smsCode":"1234"}'
```
*(В ответе финальный терминальный статус `SIGNED`).*

### 6. Альтернативный сценарий: Ручной отказ андеррайтером (Reject):
```bash
curl -s -X POST "http://localhost:8080/api/v1/employee/applications/$APP_ID/reject" \
  -H "Authorization: Bearer $EMPLOYEE_TOKEN" \
  -H "Content-Type: application/json" \
  -d '{
    "comment": "Высокая долговая нагрузка группы связанных компаний"
  }'
```
*(В ответе статус `REJECTED` с зафиксированной причиной в `rejectionReason`).*

### 7. Сценарий перезапуска конвейера при техническом сбое (Retry):
```bash
curl -s -X POST "http://localhost:8080/api/v1/employee/applications/$APP_ID/retry" \
  -H "Authorization: Bearer $EMPLOYEE_TOKEN"
```
*(Заявка переходит в `PROCESSING`, и скоринг возобновляется).*
